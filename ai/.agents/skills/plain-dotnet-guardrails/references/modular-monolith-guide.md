# Modular Monolith Guide

What a module is, bounded context rules, and how modules are structured in Plain Concepts .NET solutions.

## What Is a Module?

A module is a **self-contained bounded context** with its own domain model, use cases, persistence, and tests. Each module maps to exactly one business capability ÔÇö for example: Orders, Products, Customers, Inventory.

Modules do **not** share database tables, domain entities, or implementation code. They communicate only through well-defined Contracts.

## Every Module = 4 Projects

A module always consists of exactly four .NET projects:

| Project | Purpose |
|---------|---------|
| `{ProjectName}.Modules.{Module}` | Main module: domain entities, use cases (features), persistence (DbContext), DI registration |
| `{ProjectName}.Modules.{Module}.Contracts` | Public contract surface: domain events (`IDomainEvent`) and service interfaces ÔÇö NO implementations |
| `{ProjectName}.Modules.{Module}.UnitTests` | Domain entity unit tests (xUnit + Shouldly) |
| `{ProjectName}.Modules.{Module}.FunctionalTests` | End-to-end API tests using Testcontainers (real database, full stack) |

## IModule Pattern

Every module registers itself by implementing `ModuleBase` (which implements `IModule`):

```csharp
public sealed class OrdersModule : ModuleBase
{
    public override void Add(IHostApplicationBuilder builder)
    {
        // 1. Register handlers and validators via Scrutor
        builder.Services.AddHandlersFromAssembly(typeof(OrdersModule).Assembly);
        builder.Services.AddValidatorsFromAssembly(typeof(OrdersModule).Assembly);

        // 2. Wire per-module DbContext (connection string injected by Aspire)
        builder.Services.AddModulePersistence<OrdersDbContext>(
            Constants.Infrastructure.Components.Database.SqlServer);

        // 3. Register OpenTelemetry instrumentation
        builder.Services.AddSingleton<OrdersInstrumentation>();
    }

    public override void Initialize(IApplicationBuilder app)
    {
        // Runs EF migrations automatically in Development
        if (app.ApplicationServices.GetRequiredService<IHostEnvironment>().IsDevelopment())
        {
            using var scope = app.ApplicationServices.CreateScope();
            scope.ServiceProvider.GetRequiredService<OrdersDbContext>().Database.Migrate();
        }
    }
}
```

`RegisterAppModules()` in `Program.cs` discovers and calls `Add()` on all `IModule` implementations found in loaded assemblies.

## Per-Module Database Schema

Each module owns its own database schema to avoid table name collisions:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.HasDefaultSchema("orders");   // ÔåÉ module-specific schema
    modelBuilder.ApplyConfigurationsFromAssembly(typeof(OrdersDbContext).Assembly);
    base.OnModelCreating(modelBuilder);
}
```

This means the `Products` table in the Orders module is `orders.Products`, while the same-named table in another module would be `catalog.Products` ÔÇö no collision.

## Contracts Project Rules

The `{Module}.Contracts` project MUST contain ONLY:
- `record` domain events implementing `IDomainEvent`
- `interface` service contracts (not implementations)

The `{Module}.Contracts` project MUST NOT contain:
- EF entity classes
- Handler implementations
- DbContext or migrations
- Any reference to other module projects

```csharp
// Allowed in Contracts
public record OrderCreatedEvent(Guid OrderId, decimal Total) : IDomainEvent;
public interface IOrderService { Task<decimal> GetOrderTotalAsync(Guid orderId); }

// NOT allowed in Contracts
public class Order { ... }           // domain entity ÔÇö belongs in main module
public class OrdersDbContext { ... } // persistence ÔÇö belongs in main module
```

## Adding a Migration Manually

```bash
dotnet ef migrations add InitialCreate \
  --project src/modules/{ModuleName}/{ProjectName}.Modules.{ModuleName} \
  --startup-project src/root/{ProjectName}.Server
```

Migrations are not generated by the skills (by design ÔÇö D-33). This command is documented here and in `manual-module-guide.md` as the required post-scaffold step.

## Module Discovery Requirements

For `RegisterAppModules()` to discover a module, the module assembly must be loaded at startup. This is ensured by adding a direct project reference from `{ProjectName}.Server.csproj` to the module's `.csproj`:

```xml
<!-- In {ProjectName}.Server.csproj -->
<ItemGroup>
    <ProjectReference Include="..\..\modules\Orders\{ProjectName}.Modules.Orders\{ProjectName}.Modules.Orders.csproj" />
</ItemGroup>
```

Without this reference, the module assembly is not loaded and `RegisterAppModules()` will not find it.
